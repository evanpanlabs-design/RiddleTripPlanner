# 讨论 1：核心交付物信息架构

> 状态：🟢 已达共识 | 当前版本：v2.1（2026-09-21，Q7 模板确认，讨论 1 正式关闭）
> 讨论目标：定义 Riddle 核心交付物的领域模型（语义层）、展示区块（展示层）、确定性分级与生命周期。

## 1. 分层框架（v1 确立）

- **语义层（领域模型）**：旅行方案 = Node-Edge-Node 图 + 图上挂载的 Events。所有生成、校验、变更、回滚发生在这一层。
- **展示层（区块视图）**：B1–B7 全部是对语义层的投影/渲染，不持有独立事实。

## 2. 语义层：领域模型（v1 确立，v2 补充共识）

### 2.1 Event（事件）
旅行的语义单元：点位中的游览/消费/就餐（锚定 Node），或一段交通（锚定 Edge）。
**v2 补充**：Event 携带可选"总开销"记录字段（用户手工记账粒度，见共识 C1）；跨日 Event 允许被 T 与 T+1 两日同时引用（见共识 C11）。

### 2.2 Node-Edge-Node 图（NEN）
- **Node** = POI 或 AOI。属性 schema（共识 C9）：坐标 + 营业时间 + 类别标签为通用字段，按类别有差异字段。
- **Edge** = 路由。属性 schema（共识 C9）：交通方式（飞机/火车/地铁/驾车/公交/骑行/步行）+ 线本体（节点坐标序列）+ 里程 + 耗时。

### 2.3 完整性约束（v2 修正表述）
"无悬挂"原则**仅适用于方案链条内部**：方案图内的每个 Event 必须锚定 Node/Edge，每个图元素必须承载 Event。**候选池不属于方案**，不受此约束（共识 C5）。

### 2.4 候选池（Candidate Pool，第一类实体，共识 C5）
需求明确阶段的合法暂存区：攻略解析出的点位、用户提及未落图的地点先入池，经评估后转正落图或弃置。池内元素不参与方案校验。

### 2.5 锚点类型（共识 C6，扩展用户原提案）
- **住宿锚点**：酒店等，约束每日起终点。
- **场站锚点**：机场/火车站/码头，与住宿锚点同级的硬约束。
锚点迁移是最高影响级别的图操作，传播规则见 §6 Q7。

### 2.6 辅助决策信息
营业时间段、每周营业区间（周一闭馆类）、Event 推荐时间段（外部时间 API 推导，如日出 4:45 → 推荐 4:30–5:30）、距离/耗时。
**时间信息获取策略（共识 C10）**：先由 LLM 知识推理大致时间；无法推理则**留空**，待用户外部查询后回填，下轮统一处理。这契合 Copilot 哲学——用户对 API 提供的信息未必置信，自己查到的最信。

### 2.7 数据与地图底座
地理信息与地图绘制全部依赖高德（Amap）MCP + API（项目空间已有积累）。

## 3. 规划阶段状态机（v2 定稿）

`需求明确` → `规划中` → `准备中` → `READY`

- **不做行中与复盘阶段**（共识 C2）。
- **阶段可逆**（共识 C8）：READY 后修改方案（如换酒店）自动降级回"准备中"并复活关联 checklist 项。
- 每次用户输入 = 对图的一组操作；**回滚采用操作日志（event sourcing）**，非整版快照（共识 C8）。

## 4. 展示层：区块模型（v0 保留，v2 更新）

| 区块 | 内容 | 语义层来源 | 确定性 |
|------|------|-----------|--------|
| B1 行程总览 | 目的地/天数/节奏/预算概览 | 图元数据 + Event 开销字段聚合（只读） | L1 |
| B2 每日日程 | 按天 Event 序列 + 交通衔接 | 图按日切片投影（跨日 Event 被相邻两日引用） | **L0** |
| B3 地图视图 | 点位/路线/片区渲染 | 图的纯渲染（高德） | L0 |
| B4 住宿建议 | 片区推荐+预算带+理由 | 住宿锚点推荐决策 | L1+ |
| B5 大交通建议 | 长距 Edge 选项对比+购票时限 | 场站锚点间 Edge 候选集 | L1+ |
| B6 准备清单 | 分类任务+相对截止+执行方式 | 从图派生的 readiness 视图 | L1 |
| B7 信息附录 | 贴士/注意事项 | 自由生成区 | L2 |

**不做预算账本**（共识 C1）：仅允许用户在相关 Event 上记录总开销，B1 只读聚合，不做分摊/结算/多币种。

## 5. 确定性分级体系（v0 保留）

| 等级 | 含义 | 生产管线 | 质量门禁 |
|------|------|----------|----------|
| L0 | 事实性内容，错即事故 | 数据源直取（高德/外部时间 API/用户回填） | 数据源校验，模型禁入 |
| L1 | 结构化决策 | Jev 判定 / LLM 生成+Jev 校验 | 置信度阈值，不达标打回或转用户确认 |
| L2 | 生成式参考内容 | LLM 生成 | Jev 抽检 + 免责标注 |

## 6. 开放问题裁决记录

### ✅ 已达共识（C1–C10，对应 Q1–Q11 中 9 项）

- **C1（Q1）**：不做预算账本；Event 允许记录总开销，总览只读聚合。
- **C2（Q2/Q4）**：不做行中、不做复盘；状态机终止于 READY（且可逆）。
- **C3（Q3）**：不做多人协作。
- **C5（Q5）**：候选池是必要的第一类实体；无悬挂约束只针对方案链条，不针对候选池。
- **C6（Q6）**：锚点 = 住宿 + 场站（机场/火车站/码头）两类；锚点迁移引发连锁重排。
- **C8（Q8）**：回滚 = 操作日志（event sourcing）；阶段可逆。
- **C9（Q9）**：Node 通用字段 = 坐标+营业时间+类别标签（类别差异字段另附）；Edge = 交通方式+线本体+里程+耗时。
- **C10（Q10）**：时间锚定信息先 LLM 推理，推理不出则留空待用户回填、下轮统一处理。**衍生商业洞察**：用户自填优先原则未来可延伸为 OTA 导购位——产品具备用户规模与议价能力后，引入更优惠的 OTA 供给并收取流量/佣金费用（"你们的产品在我的应用上展示推荐就要给平台花钱"）。已同步至 README 商业模式线索。
- **C11（Q11）**：跨日 Event（如 20:00–次日 9:00 卧铺）同时承担住宿+交通语义，被 T 与 T+1 两日引用；空间锚点 T 日=出发场站、T+1 日=到达场站；语义闭环验证 = 链条时间连续 + 空间锚点衔接，无验证难度。

### ✅ Q7 变更传播（共识 C7，v2.1 关闭）

**共识**：传播范围由整体行程语义决定——单点日长途线（青甘大环线型，删一个点牵动前后两日）与高密度 citywalk（天津意风区型，删一个点仅影响前后 10 分钟两个 Event）的传播半径完全不同。用户已确认：三级半径够用；半径由 Jev 判定 + 低置信度转**异步 HITL**（不阻塞流程，用户稍后回复，与 C10"下轮统一处理"哲学一致）；模板字段认可。

**传播留档模板 v1（已确认，兼顾留档与 Agent 操作）**

每次图操作产生一条结构化传播记录：

```
PropagationRecord {
  op_id:            string          # 关联 event sourcing 日志
  op_type:          add | remove | replace | move
  target:           entity_ref      # 被操作的 Node/Edge/Event
  radius:           R1 | R2 | R3    # 传播半径（见下）
  radius_judgment:  { by: "jev", confidence: 0.0-1.0 }
  affected: [
    { entity: entity_ref,
      change: time_recalc | invalidate | resequence | needs_confirm }
  ]
  auto_apply:       bool            # 置信度达标→true；否则转用户确认
  undo_ref:         op_id           # 回滚指针
}
```

传播半径三级：
- **R1 局部**：仅相邻 Event 微调（典型：citywalk 删点，±2 Event、±30min 内）
- **R2 当日**：当天序列与时间窗整体重排（典型：换同片区酒店、增删主要景点）
- **R3 跨日**：前后日联动调整（典型：单点日删点、场站锚点变更、跨日 Event 改动）

半径判定维度（Jev 输入）：当日点位密度、Edge 耗时占当日时长比、被操作对象是否为锚点（锚点→至少 R2）、被删点的当日不可替代性（唯一目的点→R3）。
